# Contributing to SrP-CFG

Thanks for taking the time to improve SrP-CFG. This guide covers the practical
parts: how to set up the repo, what to run before opening a pull request, and the
conventions the project already follows.

By participating you agree to our [Code of Conduct](CODE_OF_CONDUCT.md).

---

## Ways to Contribute

| Type | Where |
| :--- | :--- |
| Bug report | [Open an issue](https://github.com/RolinShmily/SrP-CFG_ForCS2/issues/new?template=bug_report.yml) |
| Feature request | [Open an issue](https://github.com/RolinShmily/SrP-CFG_ForCS2/issues/new?template=feature_request.yml) |
| Keybind / convar tuning | `config/srp-cfg/**` |
| Mode or feature module | `config/srp-cfg/modes/**`, `config/srp-cfg/features/**` |
| Documentation & user guides | `app/website/content/docs/**` |
| Website / desktop UI | `app/website/**`, `app/desktop/**` |
| Translation | Any `*.md` file with a `.zh-CN.md` (or English) counterpart |

## Environment Setup

**Prerequisites** — Node.js 22+, pnpm 10+, Rust stable (MSVC toolchain, only for
desktop builds), Python 3.12 with `PyYAML` (only for config validation).

```bash
git clone https://github.com/RolinShmily/SrP-CFG_ForCS2.git
cd SrP-CFG_ForCS2
pnpm install

pnpm dev:web        # website & docs dev server
pnpm dev:desktop    # desktop suite (Tauri dev)
```

Release packaging and desktop builds are out of scope for most contributions —
see [`README.md`](README.md) for the full build matrix.

## Ground Rules for `config/`

This is where most contributions land, and where correctness matters most.

- **Never `exec` an absolute or user-specific path.** All includes are relative to
  `game/csgo/cfg/` so the packages stay relocatable.
- **Do not touch `config/srp-cfg/user/custom.cfg`'s ownership model.** Layer C is
  user-exclusive; runtime code must never write to it.
- **Keep the four-layer boundary.** Aliases and registrations belong in
  `runtime/`; per-session behaviour belongs in `modes/`; persistent personal state
  belongs to the user layer.
- **Every feature/mode directory stays self-consistent**:
  `settings.cfg` (values), `keymap.cfg` (bindings), `runtime.cfg` (logic),
  `help.cfg` (console help), `with-keymap.cfg` (opt-in keymap entrypoint).
- **Comments use `//`**, either on their own line or trailing a command — never `/* */`.
  The house style is **English first, Chinese inline after the `//`** on definition
  lines, so both audiences can read the file:
  ```cfg
  // Persistent autoview command vocabulary.
  alias "view_0" "v06" // 将 alias view_0 转发到 v06。
  ```
- **Keep each command on a single line.** CS2 parses line by line, so never indent a
  command and never break it across lines.
- **No generated files in a pull request.** `config/**` is the source of truth;
  `.github/data/config-knowledge/*.json` is regenerated by the
  [Sync SrP-CFG Knowledge Index](.github/workflows/sync-config-index.yml) workflow on merge.
  Likewise, do not hand-edit `app/website/public/data/commands.json`,
  `app/website/public/fonts/**`, or `app/website/src/styles/fonts/**`.

## Verify Before You Push

Run the checks that CI runs. Each one is dependency-light and completes in
seconds:

```bash
# 1. CFG architecture, layering and packaging rules
python3 .github/scripts/validate_cfg.py

# 2. Knowledge index: unit tests + drift-free dry-run rebuild
node --test .github/scripts/sync_config_vectorize.test.mjs
node .github/scripts/sync_config_vectorize.mjs --dry-run

# 3. Website AI stream / worker unit tests
node --experimental-strip-types --test app/website/src/lib/ai-stream.test.ts app/website/src/worker.test.ts

# 4. Desktop Rust core (only if you touched app/desktop)
cargo test -p srp-cfg-core --manifest-path app/desktop/src-tauri/Cargo.toml
```

## Commit Messages

The history follows [Conventional Commits](https://www.conventionalcommits.org/):

```text
<type>(<scope>): <subject>
```

Common types: `feat`, `fix`, `refactor`, `docs`, `chore`, `perf`, `release`.
Common scopes: `config`, `website`, `desktop`, `ci`, `deps`.

```text
feat(config): add nuke spawn preset for practice mode
fix(desktop): keep the VCFG editor from overwriting the user layer
docs(website): document the four-layer architecture model
```

Keep the subject imperative and under ~72 characters. Use the body to explain
*why*, not *what*.

## Branches and Pull Requests

1. Fork the repository and branch off `main`
   (e.g. `feat/nuke-spawn-preset`, `fix/vcfg-overwrite`).
2. Make focused commits — one logical change per commit.
3. Fill in the pull request template completely; link the issue it closes.
4. Make sure CI is green, then request review.

Small, self-contained pull requests get reviewed and merged fastest. For
architectural changes to the runtime layers or the decoupled package layout,
please open an issue to discuss the design before writing code.

Thanks for contributing.
